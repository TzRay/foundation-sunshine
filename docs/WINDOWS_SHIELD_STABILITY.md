# Windows Sunshine 与 SHIELD：问题边界、修复及联合验收

评估日期：2026-10-28。服务端基线：`5d7e5a25b4278107cdfd5cb58a247635623433d3`。
配套客户端：`TzRay/moonlight-vplus` 的 `codex/windows-shield-stream-stability` 分支。

## 1. 结论与证据边界

本轮优先修复可以从代码和测试确认的正确性问题，再提供默认关闭的发送节奏实验。
没有在 Windows GPU 或 SHIELD 上运行，不能把预期收益写成实测的画质、音质或毫秒改善。

此前《SHIELD Pro 串流分析结论》的约 100ms 呈现间隔、3 次不可恢复视频帧和 1 次音频序号缺口，
可以定位调查窗口，不能单凭 CPU0 占用或网卡峰值确定根因。报告中的 APK 与当前源码也不是同一版本。
本轮没有原始 CSV/JSONL，未重新计算那次半小时统计。

以下判断需要纠正或补全：

- `WSAEINVAL` 不等于“不支持 USO”；它也可能与源地址或调用参数有关。不能永久缓存为能力缺失。
- 批量发送成功只说明传输层接受，不保证 NIC 发出或客户端收到。未知失败也不能一律假定零发送后重放整批。
- 约 800Mbps 的帧内发送节奏本身不是错误；小批次是否更适合 SHIELD，需要相同构建的 A/B 数据。
- 有界队列溢出后清空数据会丢失视频参考帧；恢复必须处理参考链，单纯计数或增大队列不够。
- NVENC `NEED_MORE_INPUT` 不代表上一份输入/输出资源已完成，可以再次复用。
- IP 分片计数是整机观测，不能直接归因于视频包过大；USO 批次也不等于线上一个大 UDP 包。

## 2. 本轮变更及负面影响

| 优先级 / 问题 | 修复 | 预期收益 | 代价与限制 |
| --- | --- | --- | --- |
| P1：event/queue 的 `peek()`、`running()` 无锁读取共享状态 | 与写入使用同一互斥锁 | 消除已复现的数据竞争，停止状态可靠可见 | 多一次短临界区；不保证消除操作系统调度迟到 |
| P1：编码队列溢出后继续发送依赖帧 | 在出队时原子读取丢弃计数；每会话等待保留下来的 IDR，按需请求新 IDR | 避免发送已断参考链的连续 P 帧，恢复行为可解释 | 恢复前有短暂停顿，IDR 较大；共享队列使其他会话也可能保守地请求 IDR；PyroWave 保留自己的块恢复 |
| P1：批量发送只有 bool，回退可能重放已接受前缀 | 返回接受数量、状态和错误码；仅重发确定尚未接受的后缀 | 避免重复发送、识别拥塞与能力回退、保留源地址自愈 | `WOULDBLOCK` 和接受情况未知时放弃剩余批次，极端拥塞下可能增加可见丢失；避免无限等待和盲目重发不等于保证送达 |
| P1：加密前缀未计入 64KiB 批次上限 | 按每包载荷加 32 字节前缀计算批次；校验 RTSP 包长 | 批次上限与实际提交字节一致 | 某些配置下每批包数略降、系统调用略增；不会改变网络包载荷格式 |
| P1：NVENC 单套在途资源与 lookahead 不匹配 | 当前后端关闭 lookahead 并记录警告；意外 `NEED_MORE_INPUT` 终止该编码路径，不继续复用 | 避免把尚未完成的资源当成已完成帧 | 默认 lookahead=0 不受影响；手动开启者可能失去压缩效率，后续应实现完整多缓冲生命周期再开放 |
| P1：实际音频格式与总带宽预留不一致 | PCM 按采样率、声道和位深计算；AC3/E-AC3 与实际编码器限制一致；加入 4+2 音频 FEC | 固定总码率的分配更符合真实音频开销 | 固定总预算下可能降低视频编码码率；过低初始预算返回 400，过低动态请求保留上次预算；这仍是名义预算，不是严格线上限速 |
| P2：动态码率只部分更新 VBV，HEVC 升码率强制 reset/IDR | AVC/HEVC/AV1 同步按比例更新峰值码率、VBV 大小及初始延迟，保留驱动默认零值；码率变化不强制 IDR | 减少调整码率时不必要的大帧和参考链重置，保持初始化时的缓冲时长策略 | 驱动可能拒绝某些组合；失败时不提交新 rcParams，需要目标 GPU/驱动回归 |
| P2：计时器设置失败仍无限等待 | 检查设置返回值，设置失败退回休眠；等待有上界 | 避免未启动计时器使共享发送线程永久阻塞 | 故障等待仍可能约为请求时长加 100ms；不是正常路径抖动已降低的证明 |
| 实验：大批次与迟到后的补发突发 | 协商 `smooth-v1`，最多 16 包一批，按实际唤醒时间设置下一期限 | 可能降低瞬时包突发和客户端收包尾延迟 | 增加系统调用/唤醒，可能增加帧发送完成时间和 CPU；默认关闭，多会话没有统一 NIC 带宽整形 |
| 诊断：发送失败、恢复与尾延迟不可区分 | 每帧汇总发送统计，保留 p99/max；JSON 构造和排序移出采样锁 | 更容易区分主机发送、队列丢弃与客户端接收问题 | 采样仍有开销；240 个样本的滑动窗口不是整个会话 p99，也不是持久异常记录 |

Linux/macOS 只做共享发送接口的配套适配。Linux 的 `sendmmsg`/GSO 保留已接受前缀，拥塞时不再无限 poll；
macOS 返回单包发送回退。没有进行这些平台的完整产品构建。

## 3. 音频预算的具体影响

48kHz、16bit、7.1 PCM 的有效载荷为 `48000 × 16 × 8 = 6.144Mbps`。
四个数据包加两个校验包使名义音频预留为 `9.216Mbps`，另有 RTP/IP/加密及视频开销。
旧代码在高质量 8 声道下只预留 `256 × 8 = 2.048Mbps`，并可能进一步按总预算比例截断。

这次没有改变采样率、位深、声道数、音频编码格式或 FEC 比例。变化在于同一个总预算如何分配：
如总预算 200Mbps、视频 FEC 20%、固定传输预留 0.5Mbps，视频编码目标由约 164.543Mbps 变为 158.570Mbps。
如果希望保留原来的视频净码率，需要相应增加总预算，并重新确认链路容量。
小帧 FEC 向上取整、编码器突发、协议头开销意味着该预算仍不能被解释为严格的 NIC 速率上限。

### 报告中的三片重组：需要验证的假设

如果现场实际使用的是上述 PCM，且每音频包 5ms：每个原始包是 3840 字节，每秒 200 个数据包；
4+2 FEC 后约 300 个 UDP 包/秒。在 MTU 1500 下每包约需三片，30 分钟约 540000 次重组、1620000 个分片，
与报告的 539942 / 1619826 很接近。这是一个优先抓包验证的解释，尚不能确认就是音频来源。
报告重组失败为零，也不能据此认定分片造成了那次 100ms 停顿。

本轮不改变音频包格式。后续若验证属实，可协商 MTU 感知的 PCM 分块，在保持采样内容和声道的同时消除 IP 分片；
必须同时定义帧序号、样本时钟、加密和 FEC 分组，以及新旧版本回退，不能简单把 5ms 改成 1ms 后忽略包率上涨。

## 4. 两端协商与兼容

1. Sunshine `/serverinfo` 增加 `VideoPacingModes=smooth-v1`。
2. Moonlight 的“主机平滑发送（实验）”默认关闭。只有开启且非 NVIDIA 原版主机明确公布该能力，才在 `/launch`、`/resume` 发送 `videoPacing=smooth-v1`。
3. Sunshine 将选择保存在会话内，并在成功响应里返回 `videoPacing`。未知值、未请求或旧客户端保留旧发送节奏。
4. 客户端只有收到相同版本的确认才记录已启用。旧主机不需要认识新字段，客户端也不会强行改变其行为。

实验只改变批次及期限计算，不主动修改 HDR、编码器质量参数、目标码率或 FEC；音频预算修复是独立的默认正确性变更。
设置修改后重新连接。关闭开关并重连即可撤回实验，无需回退其他修复。

## 5. 诊断字段的含义

通过现有、已认证的 `/api/perf/current` 查看每个会话的 `transport`：

- `frame_send`：完整帧的主机打包/FEC/加密/等待/发送处理耗时；按帧记录一次，不按 FEC 块重复记。
- `pacer_lateness`：该帧等待期限的最大迟到；不是主机到客户端单程延迟。
- `packets_attempted`、`packets_accepted`：请求发送的数据报数量和已知被 socket 接受的数量。
- `packets_not_confirmed`：两者之差；接受状态未知也包含在内，不能直接当作网络丢包数。
- `fallback_batches`、`failed_batches`、`would_block_batches`、`last_batch_error`：回退、未完全确认、拥塞及最近错误。
- `queue_overflows`：该会话观察到共享队列丢弃计数变化的次数，不是精确的该会话丢帧数量。
- `recovery_discards`、`recovery_idr_requests`：参考链恢复期间的丢弃与 IDR 请求。
- `audio_data_failures`、`audio_fec_failures`：音频数据/校验包发送调用失败次数。

延迟窗口保留长停顿，返回 p95、p99、max 与样本数；窗口最多 240 个样本。
如需半小时分析，应周期采集并保存原始时间戳、窗口与累计计数，不能把多个窗口 p99 平均成会话 p99。

## 6. 验证状态与实机验收

本地已运行：

- 发送/队列恢复/预算/码率策略 13 项单元测试通过；同组 ThreadSanitizer 通过。
- 原有 FEC/预算测试 18 项通过，包含准确保留音频/传输预算后的期望值更新。
- 性能快照与帧率统计 19 项通过，包含 100ms 长样本、发送计数及结束会话冻结。
- `git diff --check` 通过。

Windows 专用错误分类另有一项测试，由 Windows CI 执行。完整 Windows 编译与 CTest 以本 PR 的 Actions 为准。
本地测试不能验证真实 Winsock/NIC、NVENC、Windows 定时器、HDR 显示链或 HDMI 音频路由。

建议按以下顺序验收，每组至少相同场景运行 30 分钟，并回跑基线：

1. 记录双方提交、Windows/GPU 驱动、SHIELD 系统、网卡/MTU、4K60 HEVC Main10 HDR、音频格式和总/净视频码率。
2. 同一新构建，先关闭两个实验开关，确认正确性修复后的基线；采样主机 transport 和客户端 `SD[...]`。
3. 只打开主机平滑发送，重新连接，确认两端 `smooth-v1` 日志，再比较不可恢复视频帧、音频缺口、长呈现间隔、p99/max、CPU。
4. 单独评估客户端避开 CPU0；不要与 pacing 同时切换后把变化归给其中一项。
5. 测试启动/重连、HDR 开关、多声道 PCM/Opus、码率上下调整、自动 FEC 调整、网络拥塞、源地址变化及两会话。
6. 验证旧客户端连新主机、新客户端连旧主机和开关关闭的回退；编码器不支持某格式时保持原有协商结果。

通过标准是异常率/尾延迟改善且编码质量、HDR/色彩、声道、CPU 和停止/恢复没有不可接受回退。
CPU0 降低或平均延迟降低本身不够；HDR/HDMI 应以实际画面、声道测试及路由信息验证。

## 7. 下一阶段的两端改造

| 方向 | 开始条件 | 收益与风险 |
| --- | --- | --- |
| MTU 感知的 PCM 无损分块 | 音频端口抓包证实分片来源 | 减少 IP 重组；需要新协议版本，额外包头/包率可能抵消 CPU 收益 |
| 视频净码率与总链路预算分别展示/协商 | 明确用户希望固定哪一个目标 | 避免声道/FEC 改变时意外降低视频质量；总预算固定时不可能无成本保留所有净码率 |
| 结合已有自动 FEC 的反馈控制 | 能区分丢包、晚到、主机排队和解码回压 | 可能减少冗余与拥塞振荡；需要迟滞和变更速率上限，不能对所有异常都加 FEC |
| AudioTrack 时间戳和占用驱动的音频缓冲 | 目标 HDMI/AVR 路由的可靠时钟与欠载数据 | 保持格式前提下降低排队；盲目缩小 buffer 会爆音或中断 |
| HDR 色彩链端到端验收 | 主机元数据、码流与显示模式可观测 | 查明色域、范围或元数据丢失造成的画质问题；不应为减少负载默认关闭 HDR 或强推不支持的 codec |
| 截止期限感知的帧恢复 | 双方可按帧号/RTP 时序关联事件 | 避免已无法赶上呈现期限的旧帧积压；主机与客户端单调时钟不能直接相减 |
| 完整 NVENC 多帧资源环 | 明确需要 lookahead 的质量档位 | 可恢复其压缩效率；增加资源与排队时延，不适合作为所有低延迟场景的默认 |
